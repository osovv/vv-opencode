# Project: vv-opencode

Public OSS package `@osovv/vv-opencode` (npm): an opinionated agentic development layer for
OpenCode. OpenCode owns the mechanics (streaming, model calls, sandbox, permissions); this package
adds a development process on top: spec-first trajectories (the vv-spec / vv-plan / vv-execute
skills), review-driven execution, a work-item state machine for multi-agent runs, semantic model
roles (`vv-role:smart` / `vv-role:fast`), safe tools (hashline edit, secrets redaction, Guardian),
a workflow plugin, a Telegram bridge, a native TUI `/context` inspector, and the `vvoc` CLI
(install / init / sync / launch / status / doctor / roles / presets / orchestration / plugin
toggles, and more).

The files in `.vv-factory/` are this repo's agent protocol guides. They are tracked in git: keep
them current, in English, and free of machine-specific paths, credentials, and internal
identifiers.

## What it is

- Language/runtime: TypeScript ESM on Bun (>= 1.3.8, `packageManager: bun@1.3.8`).
- CLI framework: citty; the binary is `vvoc`. The package is published to npm; release happens
  only via manual dispatch of `.github/workflows/publish.yml` (regular pushes never publish).
- Native OpenCode integration with a hard host window `>=2.0.18 <2.0.19` (`engines.opencode`),
  fail-closed outside the window. Pins: `@opencode/{plugin,client,schema,ai,protocol}` 2.0.18,
  `effect` 4.0.0-rc.112 (schema-owned peer), `zod` 4.1.8, `@opentui/*` 0.5.12, `solid-js` 1.9.15.
  There are no `@opencode-ai/*` dependencies.
- 11 server plugins plus a native TUI plugin; a single pinned entry in the native `plugins` array
  serves both the `./server` and `./tui` exports.
- The repo is GRACE 4-managed: durable state lives in `.grace/` (context / graph / verification /
  changes).

## Where to look

- `AGENTS.md` — the main entry point: GRACE protocol, repository map, change-impact table, and
  the full list of verification commands. Read it first.
- `src/cli.ts` — CLI command tree; `src/commands/*.ts` — command implementations (with colocated
  tests).
- `src/lib/` — config layers (`config-layers.ts`, `vvoc-paths.ts`), canonical config
  (`vvoc-config.ts` + `schemas/vvoc/v3.json`, a strict v3 schema), OpenCode config mutation
  (`opencode.ts`, `opencode/*`), managed agents/skills, model roles.
- `src/plugins/` — the server plugins; `src/plugins/workflow/` — the workflow engine (protocol,
  state, transitions, persistence); `src/tui.tsx`, `src/tui/context/` — the TUI.
- `scripts/e2e-v2.ts` + `scripts/e2e-v2/*` — the real-host acceptance harness (core/full/tui/list
  modes).
- `scripts/release-*.ts` — release automation (policy in `.grace/context/deployment.xml`).
- `.grace/graph/index.xml`, `.grace/verification/index.xml` — navigation over modules (`M-*`) and
  verifications (`V-M-*`); file-local anchors such as `START_MODULE_CONTRACT` live in the sources.
- `README.md` — the public CLI/setup contract; sync it whenever commands/exports change.
- `dist/` — generated by `bun run build`; never edit it by hand.

## Facts that matter

- **Fresh clone without a build**: `bun run check` passes, but 9 host-smoke unit tests are
  skipped — they require the `VVOC_E2E_V2_HOST` env var (path to the pinned host binary) and a
  built `dist/`. Current numbers: `.vv-factory/known-flakes.md`.
- **Host binary for e2e**: the harness pins the host sha256 (see `scripts/e2e-v2/host.ts`) and
  refuses to run against a different build. It does not scan `PATH` — point `VVOC_E2E_V2_HOST` at
  your local pinned opencode 2.0.18 binary.
- **npm**: only `npm pack --dry-run` inside `pack:check`/release scripts needs it, and it must be
  a real npm on `PATH` — a corepack npm shim does not work here because `packageManager` is bun.
  Details: `environment.md`.
- **grace CLI**: use the installed stable grace binary (install convention in “GRACE CLI Checks”
  in AGENTS.md). `grace lint --path .` is mandatory whenever `.grace/` artifacts change.
- Config safety: never clobber a user config; writes are conservative and idempotent; a broken or
  outdated vvoc config must fail with diagnostics instead of silently self-healing. Global
  entries go to `$XDG_CONFIG_HOME/{opencode,vvoc}`, data to `$XDG_DATA_HOME/vvoc`; project scope
  writes only inside `.opencode` and `.vvoc`.
- Commits follow Conventional Commits (`@commitlint/config-conventional`); the lefthook pre-commit
  hook runs lint + typecheck + fmt:check + check-exports in parallel.
- CI has a single release workflow; regular branches get no tests and no lint, so the local
  checks in `verify.md` are the only gate.
